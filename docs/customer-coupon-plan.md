# 손님 정보 입력 및 쿠폰 결제 기획서

작성일: 2026-10-31  
상태: 기능 구현 및 로컬 검증 완료. 운영 Supabase SQL 적용·배포 전.

## 1. 목표와 범위

직원이 주문 전에 손님 유형과 이름을 확인하고, 관리자에게 등록된 쿠폰 잔액으로 결제할 수 있도록 한다. 쿠폰은 **장수가 아닌 금액(원)**으로 관리하며, **주문 접수 성공 시 사용 금액을 자동 차감**한다. 이 두 가지는 사용자 확인을 받은 요구사항이다.

이번 범위는 손님 정보 입력, 관리자 쿠폰 등록·추가 충전, 주문 화면 잔액 표시, 쿠폰·현금·혼합 결제, 초과 납부액의 쿠폰 적립, 필요 시 계정 자동 생성이다. 주문·차감·적립·계정 생성을 일괄 저장한다. 주문 취소·환불·직원 권한 체계 확장은 포함하지 않는다.

## 2. 손님 정보 입력 흐름

기존 직원용 주문 링크로 접속하면 PIN 확인 후 손님 정보 화면을 먼저 표시한다. 기존 공유 링크를 유지하고, 페이지 내부 단계를 전환하는 방식을 우선한다.

| 선택 유형 | 필수 입력 | 다음 동작 |
| --- | --- | --- |
| 외부자 | 이름(선택) | 이름 입력 또는 생략 후 ‘주문 받기’ |
| 개척자 | 개척자 이름 | 이름 입력 후 ‘주문 받기’ |
| 지체 손님 | 지체 이름, 손님 이름 | 두 이름 입력 후 ‘주문 받기’ |

- 이름의 앞뒤 공백을 제거한다. 개척자·지체 손님의 필수 이름은 공백만 입력하면 진행을 막는다. 외부자는 빈 이름으로 주문할 수 있다.
- 이름을 입력한 손님은 유형과 이름(지체 손님은 지체 이름 포함)에 일치하는 쿠폰 계정을 조회한다. 외부자도 적립 계정이 있다면 잔액을 표시하고 사용할 수 있도록 제안한다.
- 주문 화면 상단에 유형·이름·쿠폰 잔액을 간단히 표시한다. 예: `개척자 김OO · 쿠폰 잔액 20,000원`, `지체 손님 박OO / 손님 이OO · 쿠폰 잔액 15,000원`.
- ‘손님 변경’으로 이전 단계에 돌아갈 수 있다. 장바구니는 유지하되, 이전 손님의 쿠폰 선택·사용 금액은 초기화한다.
- 성공적으로 주문을 접수하면 장바구니와 손님 정보를 초기화하고 손님 유형 선택 화면으로 돌아간다. 다음 손님에게 이전 손님 정보가 남지 않게 한다.
- 접수 결과가 불명확한 주문이 있으면 기존 ‘접수 확인 / 재시도’ 흐름을 우선한다. 해당 요청의 손님·결제 정보를 변경하지 않는다.

### 계정 조회와 중복 등록 정책

- 이름이 일치하는 등록 계정이 없으면 ‘등록된 쿠폰 정보 없음’을 표시한다. 손님 유형은 유지하며 현금 주문은 가능하다. 초과 납부로 적립할 때 계정이 없다면 자동 생성한다. 계정이 없을 때 기존 쿠폰 잔액을 임의로 부여하지 않는다.
- 조회 실패와 미등록을 구분한다. 조회 실패를 잔액 0원으로 표시하지 않는다. 쿠폰 결제는 재조회 성공 전까지 막는다.
- 매장과 손님 유형 안에서 외부자·개척자는 이름, 지체 손님은 지체 이름과 손님 이름의 조합으로 조회한다. 다른 매장의 계정은 조회하지 않는다.
- 같은 식별 정보의 중복 등록은 DB에서도 차단한다. 별개 동명이인은 관리자가 `홍길동`, `홍길동2`처럼 이름을 구분하여 등록한다. 지체 이름이 다르면 같은 손님 이름도 별도 계정으로 등록할 수 있다.
- 자동 생성 시 같은 식별 계정이 있으면 해당 계정을 사용하고 임의로 숫자 접미사를 붙이지 않는다. 별개 동명이인은 직원이 구분된 이름을 확인한 뒤 진행해야 한다.

## 3. 관리자 쿠폰 관리

현재 매장 관리자 화면에 ‘손님 쿠폰 관리’ 영역을 추가한다.

| 유형 | 입력 항목 |
| --- | --- |
| 외부자 | 이름, 쿠폰 금액(원). 주문에서 자동 생성된 계정도 관리 대상 |
| 개척자 | 이름, 쿠폰 금액(원) |
| 지체 손님 | 지체 이름, 손님 이름, 쿠폰 금액(원) |

목록은 유형, 지체 이름(해당 시), 이름, 남은 쿠폰 금액, 추가 충전 버튼을 보여준다. 이름 검색과 유형 선택으로 필요한 계정을 찾는다. 외부자 계정도 적립·재사용할 수 있어 관리 목록에 포함한다.

### 금액 입력 의미 — 확정 정책

- 신규 등록의 ‘쿠폰 금액’은 처음 보유한 잔액이다. 0원 이상의 정수만 허용한다.
- 기존 계정은 ‘추가 충전액(원)’을 입력한다. 양의 정수만 허용하며 현재 잔액에 더한다. 잔액을 입력값으로 교체하지 않는다.
- 저장 확인에 `현재 20,000원 + 충전 10,000원 → 예상 30,000원`을 표시한다. 실제 결과는 처리 시점의 잔액을 기준으로 한다.
- 동시 주문·충전이 있어도 최신 잔액에 가산한다. 충전 요청에도 고유 요청 ID를 사용하여 응답 단절 후 재시도·중복 클릭으로 두 번 충전되지 않게 한다.
- 관리자 변경과 주문 차감은 금액 변경 내역으로 보관한다. 화면에 복잡한 내역 관리 기능을 추가하지 않아도 변경 원인은 추적할 수 있게 한다.
- 사용 이력이 있는 계정의 이름 수정은 기존 주문의 손님 이름을 바꾸지 않는다. 이번 범위에서는 계정 삭제 기능을 두지 않는다.

## 4. 주문 화면과 결제

결제수단은 요청한 순서대로 **쿠폰 / 현금 / 쿠폰+현금**을 표시한다. 화면에는 주문 총액과 함께 쿠폰 사용액·현금 수납액을 구분한다. 기존 현금결제에 포함하던 계좌이체도 현금으로 분류한다.

| 결제수단 | 쿠폰 사용액 | 현금 수납액 | 접수 조건 |
| --- | --- | --- | --- |
| 쿠폰 | 주문 총액 | 0원 | 등록 계정과 충분한 잔액 필요 |
| 현금 | 0원 | 주문 총액 | 쿠폰 잔액과 무관 |
| 쿠폰+현금 | 직원이 입력 | 총액 − 쿠폰 사용액 | 쿠폰 사용액이 잔액 이하이고, 두 결제액 모두 양수 |

위 표의 현금 수납액은 **주문에 필요한 현금액**이다. 손님이 실제로 낸 돈은 별도의 ‘받은 현금’ 값으로 관리한다.

혼합 결제의 쿠폰 사용액은 `잔액과 주문 총액 중 작은 금액`으로 우선 제안하고 수정할 수 있게 한다. 제안값이 전액 쿠폰 결제가 되는 경우 현금액이 0원임을 표시하고 ‘쿠폰’을 선택하도록 안내한다. 0원 쿠폰 사용은 ‘현금’을 선택하도록 안내한다.

예: 주문 18,000원, 쿠폰 잔액 10,000원이면 쿠폰 10,000원 + 현금 8,000원. 접수 후 잔액은 0원이다. 잔액이 20,000원이고 쿠폰으로 전액 결제하면 접수 후 2,000원이 남는다.

### 받은 현금 입력과 초과액 적립 — 확정 정책

- 현금·쿠폰+현금 선택 시 ‘받은 현금(선택)’ 입력란을 표시한다. 비워 두면 필요한 현금액을 정확히 받은 것으로 처리한다. placeholder에 필요한 현금액을 표시하되 실제 입력값과 구분한다.
- 입력했다면 0원 이상의 정수여야 한다. 필요한 현금액보다 적으면 부족액을 표시하고 접수를 막는 것을 기본안으로 한다. 빈 입력과 숫자 0을 구분한다.
- `주문 총액 = 쿠폰 사용액 + 필요한 현금액`.
- `쿠폰 적립액 = 실제 받은 현금 − 필요한 현금액`.
- `최종 쿠폰 잔액 = 접수 직전 잔액 − 쿠폰 사용액 + 쿠폰 적립액`.
- 초과분은 현금 거스름돈이 아닌 해당 손님의 쿠폰으로 적립한다. 이번 주문의 쿠폰 사용액은 접수 전 잔액 이하여야 한다. 이번 적립액을 같은 주문의 사용 가능 잔액에 미리 더하지 않는다.
- 이름이 있는 미등록 손님은 초과액이 생기는 주문 접수 시 해당 유형으로 계정을 자동 생성한다. 이름 없는 외부자는 일반 현금 주문은 가능하지만, 적립이 필요해지면 이름 입력을 요구한다. 이름을 입력하기 전에는 적립 주문을 접수하지 않는 것을 기본안으로 한다.
- 기존 계정이 있으면 그 계정에 적립한다. 계정 생성·차감·적립·주문 저장 중 하나라도 실패하면 전부 취소한다.
- 확인 팝업에 필요한 현금액, 실제 받은 현금, 쿠폰 적립액, 차감 후 적립까지 반영한 예상 잔액을 구분해 표시한다. 초과액이 있으면 ‘초과 2,000원을 쿠폰으로 적립합니다’라고 명시한다.

| 예시 | 총액 | 기존 잔액 | 쿠폰 사용 | 필요 현금 | 받은 현금 | 적립 | 최종 잔액 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 현금 정확 납부 | 8,000 | 0 | 0 | 8,000 | 미입력 → 8,000 | 0 | 0 |
| 현금 초과 납부·계정 생성 | 8,000 | 미등록 | 0 | 8,000 | 10,000 | 2,000 | 2,000 |
| 혼합 결제 초과 납부 | 18,000 | 10,000 | 10,000 | 8,000 | 10,000 | 2,000 | 2,000 |
| 쿠폰 일부만 사용 | 18,000 | 10,000 | 5,000 | 13,000 | 15,000 | 2,000 | 7,000 |

### 기본 선택과 입력 반응

- 이름 없는 외부자 또는 쿠폰 미등록 손님: 현금 선택, 쿠폰 관련 선택지는 비활성화한다. 현금 초과 납부에 따른 적립은 가능하다.
- 등록 계정이 있는 손님: 충분한 잔액이면 쿠폰, 부족하지만 잔액이 있으면 쿠폰+현금, 잔액이 0원이면 현금을 제안한다. 혼합 결제는 쿠폰 최대 사용을 기본값으로 하고 직원이 금액을 직접 조절한다.
- 메뉴·수량 변경 시 총액과 현금액을 다시 계산한다. 쿠폰 입력값이 새로운 총액이나 최신 잔액을 넘으면 접수를 막고 수정을 안내한다.
- ‘받은 현금’이 빈칸이면 변경된 필요액을 기준으로 계산한다. 직접 입력했다면 그 값을 유지하고 부족액·적립액을 다시 계산한다. 손님 변경 시에는 받은 현금도 초기화한다.
- 주문 확인 팝업에 손님 정보, 메뉴·수량, 총액, 쿠폰 사용액, 현금 수납액, 예상 잔액을 표시한다. 현금 수납은 기존과 같이 직원이 확인하며 별도 결제대행 기능은 추가하지 않는다.
- 잔액은 화면 표시 이후 바뀔 수 있으므로 ‘접수 시 최종 확인’한다. 실시간 반영은 편의를 위한 것이며 DB 검증을 대체하지 않는다.

## 5. 저장과 동시 주문 처리

현재 `submit_order`는 주문·상세를 한 번에 저장하고 동일 요청 재시도를 중복 생성하지 않게 처리한다. 이 경계 안에 계정 생성·쿠폰 차감·초과액 적립도 포함한다. 화면에서 잔액을 먼저 변경한 뒤 주문을 따로 저장하는 구조는 사용하지 않는다.

1. 같은 요청 ID로 이미 접수된 주문이 있는지 먼저 확인한다. 같은 내용의 재시도면 기존 주문을 반환한다.
2. 손님 유형·필수 이름·매장 소속 계정·결제수단·결제 금액을 검증한다. 메뉴 가격·판매 상태 검증도 유지한다.
3. 쿠폰 계정의 현재 잔액을 잠그고 확인한다. 동시 주문으로 같은 잔액을 중복 사용하지 못하게 한다.
4. 필요한 계정 생성, 주문, 주문 상세, 쿠폰 차감, 초과액 적립, 금액 변경 내역을 같은 트랜잭션으로 저장한다. 계정이 없는 동시 요청은 같은 식별 정보에 대해 직렬화하여 계정 중복 생성·적립 누락을 방지한다.
5. 하나라도 실패하면 전체를 취소한다. 잔액 부족으로 거절된 경우 주문도 생성하지 않는다.

잔액 부족 시 손님·장바구니는 유지하고 최신 잔액을 표시한다. 직원은 혼합 결제 금액을 조정하거나 현금으로 변경한 뒤 새 요청으로 접수한다. 네트워크 단절 등 결과가 불명확한 경우에는 기존 요청 ID와 원래 손님·금액 그대로 재확인한다. 재시도로 쿠폰이 두 번 차감되지 않아야 한다.

관리자 계정 등록·추가 충전은 해당 매장 소유자에게만 허용한다. 직원 화면은 주문에 필요한 계정 조회와 주문 RPC를 사용하며, 주문에 수반되는 계정 생성과 초과액 적립만 허용한다. 잔액을 직접 수정하는 공개 UPDATE 경로는 두지 않는다. 기존 직원 PIN 구조의 권한 한계는 별도 과제로 남기며 이번 기능이 이를 해결한다고 가정하지 않는다.

## 6. 데이터 변경안

구체적인 테이블·함수 이름은 구현 단계에서 확정한다. 기존 주문을 삭제하거나 재생성하지 않는 추가 마이그레이션으로 적용한다.

| 데이터 | 주요 저장 내용 |
| --- | --- |
| 매장별 쿠폰 계정 | 매장 ID, 유형, 개척자/손님 이름, 지체 이름, 현재 잔액, 변경 시각 또는 버전 |
| 주문 추가 정보 | 손님 유형, 계정 ID(해당 시), 이름·지체 이름 스냅샷, 쿠폰 사용액, 필요 현금액, 실제 받은 현금, 쿠폰 적립액 |
| 쿠폰 금액 변경 내역 | 계정 ID, 주문 ID(주문 차감 시), 변경 종류, 증감액, 변경 전후 잔액, 시각 |
| 미확인 주문 임시 저장 | 기존 요청 정보에 손님 식별 정보·스냅샷·쿠폰 사용액·받은 현금 입력 여부와 금액 추가 |

모든 금액은 원 단위 정수로 저장한다. 잔액은 음수가 될 수 없고, 쿠폰 사용액+필요 현금액은 서버가 계산한 주문 총액과 일치해야 한다. 실제 받은 현금=필요 현금액+쿠폰 적립액도 검증한다. 실제 수납액을 주문 매출로 잘못 합산하지 않는다. 손님 유형과 결제수단의 조합도 서버에서 검증한다.

기존 주문에는 손님 정보를 ‘미기록’으로 표시한다. 기존 ‘쿠폰’ 주문은 누구의 쿠폰이었는지 알 수 없으므로 새 계정에서 소급 차감하지 않는다. 기존 현금·쿠폰 주문의 결제액은 기존 주문 상세 스냅샷을 기반으로 집계하되, 기록이 부족한 경우 미확인 값을 임의로 만들어 넣지 않는다.

기존 미확인 요청이 브라우저에 남아 있을 수 있으므로 데이터 형식 전환과 구형 RPC 호출의 호환 정책이 필요하다. 배포 전 미확인 요청 해소를 확인하고, 진행 중 재시도가 새 주문으로 바뀌지 않도록 한다. 부하테스트 스크립트의 기존 현금 주문 호출도 함께 확인한다.

## 7. 통계·CSV·다른 직원 화면

- 관리자 통계는 주문 총액, 쿠폰 사용액, 주문에 사용한 현금액, 실제 받은 현금, 초과액 쿠폰 적립을 구분한다. 관리자 추가 충전도 주문 매출과 별도 집계한다. 기존 주문 총액 통계의 의미는 유지한다.
- CSV에는 손님 유형, 개척자/손님 이름, 지체 이름, 쿠폰 사용액, 필요 현금액, 실제 받은 현금, 쿠폰 적립액을 추가한다.
- 현재 CSV는 메뉴당 한 행이다. 주문 단위 결제액을 각 메뉴 행에 반복하면 합산 시 부풀려지므로, 주문번호별 첫 메뉴 행에만 주문 쿠폰액·현금액을 기재한다는 안을 우선한다. 열 이름에도 ‘주문 합계·첫 행만’을 명시한다. 기존 메뉴 금액 열은 유지한다.
- 계정 이름을 수정해도 이미 접수된 주문·CSV는 당시 이름 스냅샷을 사용한다.
- 주방·서빙 화면의 동작은 유지한다. 손님 이름과 쿠폰 정보를 작업 화면에 추가하지 않아도 기존 주문번호·테이블번호로 업무를 수행할 수 있다.

## 8. 구현 순서와 확인 기준

1. 확정 정책과 아래 기본안을 반영한다.
2. 쿠폰 계정·변경 내역·주문 필드를 추가하고 원자적 주문 RPC를 확장한다.
3. 관리자 등록·수정 UI를 추가한다.
4. 손님 입력 단계와 주문 화면 쿠폰·결제 UI를 연결한다.
5. 확인 팝업·미확인 요청 재시도·통계·CSV·리허설 호출을 연결한다.
6. 격리된 DB와 리허설 매장에서 아래 시나리오를 확인한다.

| 확인 시나리오 | 기대 결과 |
| --- | --- |
| 외부자, 개척자, 지체 손님 입력 | 유형별 필수 입력과 다음 단계가 요구사항대로 동작 |
| 쿠폰 전액·현금 전액·혼합 결제 | 결제액 합계와 차감 후 잔액 일치 |
| 쿠폰 미등록, 조회 실패, 잔액 0원 | 서로 구별되어 표시되고 부당한 쿠폰 접수 차단 |
| 여러 직원이 같은 계정으로 동시 주문 | 잔액 이하만 승인되고 음수 잔액 없음 |
| 상세 저장 실패 또는 차감 실패 | 주문·상세·차감 모두 롤백 |
| 접수 성공 직후 응답 단절 후 재시도 | 주문 1건·차감 1회만 발생 |
| 관리자 충전과 주문 차감 동시 발생 | 충전·차감 모두 반영, 잔액 덮어쓰기 없음 |
| 충전·초과액 적립 후 응답 단절과 재시도 | 충전·적립이 한 번만 반영 |
| 받은 현금 미입력·0원·부족·초과 | 미입력은 정확 납부, 부족 입력은 차단, 초과는 정확히 적립 |
| 이름 없는 외부자의 초과 납부 | 이름 입력 후 계정 생성·적립 가능 |
| 같은 계정 동시 생성 또는 중복 등록 | 중복 계정 없음, 다른 지체의 같은 손님 이름은 허용 |
| 성공 후 다음 손님, 손님 변경 | 이전 손님의 계정·쿠폰 사용액이 섞이지 않음 |
| 기존 주문·미확인 요청·리허설 호출 | 이력 보존 및 중복 접수 방지 유지 |
| 여러 메뉴 주문 CSV | 주문 결제액 중복 집계 없음 |

## 9. 확정 사항과 남은 기본안

확정 사항: 지체 이름+손님 이름별 개별 잔액, 혼합 결제 쿠폰 최대 사용 기본값과 직접 수정, 관리자 추가 충전, 동일 식별 정보 중복 계정 차단, 외부자 이름 선택 입력, 초과 현금의 쿠폰 적립과 미등록 계정 자동 생성.

다음은 새 요구사항을 일관되게 연결하기 위한 기본안이다. 외부자 적립 계정은 이후 주문에서도 조회·사용하고 관리자 목록에서도 관리한다. 외부자가 익명으로 주문한 뒤 적립이 필요해지면 이름을 받는다. 유형이 다르면 같은 이름을 별도 계정으로 취급한다. 부족하게 받은 현금으로는 주문을 접수하지 않는다.

## 10. 적용 방법과 구현 메모

1. 진행 중인 주문 접수를 잠시 중지하고 미확인 주문 요청을 먼저 해소한다.
2. Supabase SQL Editor에서 `migrations/20261031_customer_coupons.sql` 전체를 실행한다. 기존 주문·메뉴는 보존된다. **기존 DB에서는 테이블 초기화용 `database_schema.sql`을 실행하지 않는다.**
3. 앱을 배포한 뒤 주문·관리자 페이지를 새로고침한다. 먼저 리허설 매장에서 등록, 추가 충전, 쿠폰 결제, 혼합 결제, 초과액 적립을 확인한다.

`coupon_accounts`는 유형·이름·지체 이름별 잔액을 저장하고, `coupon_transactions`는 등록·추가 충전·사용·초과액 적립을 구분한다. `submit_customer_order`가 기존 메뉴 검증 함수를 호출하고 계정 변경을 같은 트랜잭션 안에서 처리한다. `manage_coupon_account`는 매장 소유자만 실행할 수 있으며 충전 요청 재시도를 중복 반영하지 않는다.

기존 `submit_order`는 구형 미확인 주문과 현금 리허설 스크립트 호환을 위해 유지한다. 기존 주문에 쿠폰 잔액을 소급 부여하거나 차감하지 않는다. 잔액은 주문 화면에서 15초 간격·포커스 복귀·온라인 복귀·수동 버튼으로 다시 조회하고, 접수 시 DB에서 최종 검증한다. 별도 Realtime publication 설정은 필요하지 않다.

관리자 목록에서 이름은 충전 대상 식별값이므로 추가 충전 중 바꿀 수 없다. 이름 변경·계정 삭제·잔액 강제 차감은 이번 UI에 포함하지 않는다. 관리자 등록액·추가 충전 합계는 쿠폰 관리 영역에서 주문 매출과 별도로 표시한다.

검증은 로컬 격리 PostgreSQL 및 자동화된 컴포넌트·금액 계산 테스트를 사용한다. 운영 DB 적용과 실제 브라우저 화면 점검은 별도 진행이 필요하다.
