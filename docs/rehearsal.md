# 노트북 한 대로 자동 리허설

Node.js 22 이상과 프로젝트에 설치된 패키지를 사용한다. 새 패키지는 필요 없다.
프로젝트 폴더에서 실행하면 `.env.local`의 공개 Supabase URL·anon key를 읽는다.
키나 비밀번호를 채팅에 붙여넣을 필요는 없다.

## 준비할 것

1. 관리자 화면에서 이름에 ‘리허설’ 또는 ‘테스트’가 들어가는 전용 매장을 만든다.
2. 담당 구역 1~7에 판매 가능한 메뉴를 각각 최소 1개씩 등록한다.
3. 매장 ID와 정확한 매장 이름을 확인한다. 직원 링크의 `/<매장 ID>/order`에서 ID를 확인할 수 있다.
4. 지금까지 전달한 주문 접수·조리 수량·서빙 수량·소프트 삭제·통계 SQL을 적용한다.

## 설정 확인: 주문을 생성하지 않음

```powershell
node scripts/rehearsal.mjs --store-id "매장-UUID" --store-name "리허설 전용"
```

매장 ID·이름과 7개 구역의 메뉴가 맞는지 읽기만 한다.
실제 운영 매장을 잘못 선택하지 않도록 이름이 정확히 일치하고 테스트용 이름인지 검사한다.

## 짧은 동작 확인: 6건

```powershell
node scripts/rehearsal.mjs --store-id "매장-UUID" --store-name "리허설 전용" --orders 6 --rpm 12 --run
```

## 약 5분 리허설: 60건, 평균 분당 12건

```powershell
node scripts/rehearsal.mjs --store-id "매장-UUID" --store-name "리허설 전용" --orders 60 --rpm 12 --run
```

주문 담당자 6명이 동시에 접수하는 묶음을 일정 간격으로 반복한다.
주문마다 3개 주방의 메뉴를 섞고 수량은 메뉴당 1~5개로 만든다.
7개 주방 작업자가 각 구역을 처리하며, 서빙 작업자는 하나가 순서대로 처리한다.
접수가 끝나도 남은 조리·서빙이 모두 끝날 때까지 계속 실행하므로 총 시간은 늘어날 수 있다.

`--cook-ms 1000 --serve-ms 1500`을 추가하면 조리·서빙 1개 처리 사이에 지연을 넣는다.
기본 300ms는 서버 검증용 속도이며 실제 직원의 처리 속도를 의미하지 않는다.
`--orders`와 `--rpm`으로 총 주문 수와 평균 주문 속도를 조절한다.
부하는 작은 값부터 올린다. 같은 Supabase 프로젝트의 다른 매장도 서버 자원을 공유한다.

## 확인할 결과

- 주문 접수부터 조리·서빙·주문 완료까지 자동 수행한다.
- 10건마다 동일한 접수 요청을 다시 보내 주문번호·주문 ID가 유지되는지 확인한다.
- 종료 시 저장된 메뉴·수량·금액·완료 상태와 주문번호 중복을 확인한다.
- 시작 전후 통계 차이를 예상 주문 수·매출·대기 수량과 대조한다.
- API별 호출 수, p95/최대 응답 시간, 오류 및 상태 충돌 수를 JSON 보고서로 저장한다.
- 결과는 `test-results/rehearsal-<실행 ID>.json`에 남고 Git에서는 제외한다.
- 화면에는 `TEST-<실행 ID 일부>-<번호>` 형식의 테이블로 표시된다.

## 실행 중 운영

브라우저에서 테스트 매장의 주방·서빙·관리자 화면을 열어 갱신 상태를 관찰할 수 있다.
테스트 중에는 해당 매장의 주문·수량·메뉴를 직접 변경하지 않는다.
테스트는 실제 DB에 주문을 저장하며 자동 삭제하지 않는다. 행사에는 별도 실제 매장을 사용한다.
`Ctrl+C`로 중지하면 새 처리를 멈추고 진행 중인 요청을 정리한 뒤 보고서를 저장한다.
오류가 나면 중단하고 보고서의 요청 ID·테이블로 접수 여부를 확인한다. 미완료 테스트 주문은 남을 수 있다.

이 스크립트는 API 작업자 시뮬레이션이다. 브라우저 14개의 Realtime 연결·화면 조회 부하나
확인 팝업 클릭, 실제 기기의 절전·현장 와이파이까지 자동 검증하지 않는다.
