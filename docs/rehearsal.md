# 노트북 한 대로 자동 리허설

Node.js 22 이상과 프로젝트에 설치된 패키지를 사용한다. 새 패키지는 필요 없다.
프로젝트 폴더에서 실행하면 `.env.local`의 공개 Supabase URL·anon key를 읽는다.
키나 비밀번호를 채팅에 붙여넣을 필요는 없다.

## 준비할 것

1. 관리자 화면에서 이름에 ‘리허설’ 또는 ‘테스트’가 들어가는 전용 매장을 만든다.
2. 현재 판매할 일반 메뉴·구성 전용 메뉴·세트와 텍스트 옵션을 등록한다. 사용하지 않는 구역에 메뉴를 만들 필요는 없다. 실제 구성품의 주방 번호는 1~7로 설정한다.
3. 매장 ID와 정확한 매장 이름을 확인한다. 직원 링크의 `/<매장 ID>/order`에서 ID를 확인할 수 있다.
4. 지금까지 전달한 주문·쿠폰·세트·텍스트 옵션·주방 완료 시각 SQL을 모두 적용한다.

## 설정 확인: 주문을 생성하지 않음

```powershell
node scripts/rehearsal.mjs --store-id "매장-UUID" --store-name "리허설 전용"
```

매장 ID·이름과 판매 가능한 메뉴·구성을 읽기만 한다.
실제 운영 매장을 잘못 선택하지 않도록 이름이 정확히 일치하고 테스트용 이름인지 검사한다.

## 짧은 동작 확인: 6건

```powershell
node scripts/rehearsal.mjs --store-id "매장-UUID" --store-name "리허설 전용" --orders 6 --rpm 12 --run
```

## 약 5분 리허설: 60건, 평균 분당 12건

```powershell
node scripts/rehearsal.mjs --store-id "매장-UUID" --store-name "리허설 전용" --orders 60 --rpm 12 --run
```

주문 담당자 6명이 동시에 접수하는 묶음을 일정 간격으로 반복한다.
주문마다 판매 가능한 메뉴를 최대 3종씩 순환 선택하고 판매 수량은 메뉴당 1~5개로 만든다. 구성 전용 메뉴는 직접 주문하지 않으며, 품절·숨김·삭제 구성품이 있는 세트도 제외한다. 세트의 구성 수량과 옵션 선택 개수에 맞춰 요청하고 실제 담당 주방에 작업을 나눈다. 홀수 차례에는 종류를 섞고 짝수 차례에는 같은 종류를 반복 선택한다.
7개 주방 작업자가 각 구역을 처리하며, 서빙 작업자는 하나가 순서대로 처리한다.
접수가 끝나도 남은 조리·서빙이 모두 끝날 때까지 계속 실행하므로 총 시간은 늘어날 수 있다.

`--cook-ms 1000 --serve-ms 1500`을 추가하면 조리·서빙 1개 처리 사이에 지연을 넣는다.
기본 300ms는 서버 검증용 속도이며 실제 직원의 처리 속도를 의미하지 않는다.
`--orders`와 `--rpm`으로 총 주문 수와 평균 주문 속도를 조절한다.
부하는 작은 값부터 올린다. 같은 Supabase 프로젝트의 다른 매장도 서버 자원을 공유한다.

## 확인할 결과

- 주문 접수부터 조리·서빙·주문 완료까지 자동 수행한다.
- 10건마다 동일한 접수 요청을 다시 보내 주문번호·주문 ID가 유지되는지 확인한다.
- 종료 시 저장된 메뉴·수량·금액·완료 상태와 주문번호 중복을 확인한다.
- 시작 전후 통계 차이를 예상 주문 수·매출·대기 수량과 대조한다.
- API별 논리 호출 수(재시도 묶음 기준), p95/최대 소요 시간, 오류 및 상태 충돌 수를 JSON 보고서로 저장한다.
- 결과는 `test-results/rehearsal-<실행 ID>.json`에 남고 Git에서는 제외한다.
- 화면에는 `TEST-<실행 ID 일부>-<번호>` 형식의 테이블로 표시된다.

## 실행 중 운영

브라우저에서 테스트 매장의 주방·서빙·관리자 화면을 열어 갱신 상태를 관찰할 수 있다.
테스트 중에는 해당 매장의 주문·수량·메뉴를 직접 변경하지 않는다.
테스트는 실제 DB에 주문을 저장하며 자동 삭제하지 않는다. 행사에는 별도 실제 매장을 사용한다.
`Ctrl+C`로 중지하면 새 처리를 멈추고 진행 중인 요청을 정리한 뒤 보고서를 저장한다.
일시적인 502·503·504·일부 네트워크 오류는 0.5초·1초·2초 대기로 최대 3번 재시도한다. 접수는 동일 요청 ID를 유지하고 수량 변경은 동일 조건부 갱신을 재사용하며, 응답이 유실됐을 때 저장 상태를 확인한다. 재시도로 복구하지 못한 오류나 검증 실패가 나면 중단하고 보고서의 요청 ID·테이블로 접수 여부를 확인한다. 미완료 테스트 주문은 남을 수 있다.

이 스크립트는 API 작업자 시뮬레이션이다. 브라우저 14개의 Realtime 연결·화면 조회 부하나
확인 팝업 클릭, 실제 기기의 절전·현장 와이파이까지 자동 검증하지 않는다.


## 현재 세트·옵션·쿠폰 결제 검증

기본 명령은 그대로 사용할 수 있다. 예전과 달리 세트와 텍스트 선택이 있는 메뉴도 자동 포함한다. 최신 주문 화면과 같은 `submit_customer_order`를 호출하여 외부 손님·현금 결제로 접수한다. 기본 모드는 쿠폰 계정을 만들거나 기존 잔액을 바꾸지 않는다.

쿠폰과 초과 납부 적립까지 테스트하려면 다음처럼 실행한다.

```powershell
node scripts/rehearsal.mjs --store-id "매장-UUID" --store-name "리허설 전용" --orders 60 --rpm 12 --payments mixed --run
```

`mixed`는 각 주문 작업자에게 실행별 `TEST-<실행 UUID>-<작업자>` 손님 이름을 부여한다. 첫 현금 주문의 초과 납부액을 쿠폰으로 적립하고, 이후에는 그 잔액을 사용한다. 부족하면 쿠폰+현금, 충분하면 쿠폰 결제로 처리한다. 잔액이 0원이 되면 다시 현금 초과 납부로 테스트 잔액을 만든다. 기존 개척자·지체 손님·외부 손님 계정을 검색해 사용하지 않는다. 테스트 계정·적립·주문 내역은 자동 삭제하지 않으며 관리자 페이지에 남는다.

6명이 동시에 작업하므로 아주 짧은 테스트는 적립 단계만 거칠 수 있다. 결제 유형을 두루 보려면 18건 이상을 권장하되, 실제 발생 유형은 메뉴 금액에 따라 달라지므로 보고서의 `paymentCounts`를 확인한다. 모든 메뉴가 순환 선택될 만큼 주문 수를 늘려야 하며, `uncoveredMenus`가 비어 있는지도 확인한다. 모든 옵션 조합을 전수 검사하는 도구는 아니다.

검증 항목:

- `order_sales`의 판매 수량·세트 가격·구성 스냅샷과 `order_items`의 구성품별 작업 수량을 별도로 대조한다.
- 같은 탄산 구성품이 여러 세트에 있어도 판매 행 ID로 구분한다.
- 선택 결과가 판매 이력과 해당 작업 이름에 남는지 검사한다.
- 최종 조리·서빙 수량, 상태, 조리 완료 시각을 확인한다.
- 현금·쿠폰·초과액 적립 통계와 테스트 전용 계정 잔액을 확인한다.
- 보고서에는 세트·옵션 판매 행 수, 메뉴별 판매 수량, 주방별 실제 처리 수량, 재시도 이력도 기록한다.

브라우저에서 직접 CSV를 내려받거나 소리·선택 버튼·확인 팝업을 자동 조작하지는 않는다. CSV 원본인 판매 행과 금액은 API로 검증한다. 실제 화면은 별도 리허설이 필요하다. 관찰할 주방·서빙 화면은 테스트 매장으로 열고 ‘알림음 켜기’를 누르되, 자동 테스트 중 수량 버튼은 직접 누르지 않는다.

재시도가 발생한 호출의 소요 시간에는 대기·재시도 시간이 포함된다. HTTP 순수 응답 시간과 구분하여 보고서의 `retryLog`와 함께 해석한다.
